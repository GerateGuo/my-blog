llm-relay：把一堆免费额度收拢成一条 OpenAI 兼容接口

背景：免费额度很好用，但太琐碎

我给本地 AI Agent 配模型时走的是「免费额度」这条路：几家厂商各有免费档，但同一家账号里不同模型的额度互相独立（差 10 倍很常见）、限流是 key 级的、偶尔还会遇到超时、401、200 但返回空内容。

一开始我把某一家直接写死在调用方里，很快就受不了了：

  • 换一把 key 要改调用方、重启调用方；
  • 某家限流，整条链路就停在那里等；
  • 上游偶发返回「格式不对但 HTTP 200」的内容，调用方得自己判断；
  • 每个调用方都要各写一遍重试、退避、记账。

于是抽出一层中继，调用方只知道一个地址 + 一个模型名，剩下的复杂度全留在这一层。

它是什么

llm-relay 是一个单文件、纯 Python 标准库的 OpenAI 兼容中继：对外只暴露一个 /v1/chat/completions。

内容
链式兜底 每个模型给一个 chain 号，候选按「过滤 → 按 chain 升序 → 截断」构建，失败自动交给下一个
额度治理 每 provider 一个 rpm 令牌桶 + 并发闸；429 认 Retry-After，超时/5xx 冻 provider，额度耗尽停 key 一小时
冷却封顶 单次失败最多冻 120s，只有窗口内连败到阈值才允许升到 300s
响应归一化 content 空但有 reasoning 就提升上来；usage 缺失补零；tool_calls 原样透传
JSON 硬校验 要求 json_schema 时对照 schema 校验，不合格一律 502，绝不把坏内容当成功交出去
命名路由 一个模型名对应一条链 + 一套策略（免费档筛选、候选数、最小时长）
调用方隔离 具名身份各有 key、rpm、日 token 预算、允许的路由
用量记账 每次尝试一行 JSON，只记 key 序号与指纹，永不记明文

运维面板

配套一个同样零依赖的单页面板（九个标签页），候选链、Key 池、请求日志、用量统计、调用方配额、能力实测都在里面，本机免密、局域网访问需密钥且默认只读。

四个设计取舍

为什么坚持单文件 + 纯标准库。 这层的定位是「随手能跑」：克隆下来 python3 llm_relay.py 就起来了，没有依赖、没有数据库、没有构建步骤。代价是路由、Cookie、Prometheus 文本格式这些都得自己写——但这一层本来就不该有复杂抽象。

为什么冷却必须封顶。 早期版本里一次网络抖动会把 provider 冻到 900 秒，等于十五分钟里整个池子全瘫。现在单次失败最多 120s，只有短时间内连败到 3 次才允许升到 300s。一次抖动不该让一个 provider 消失。

为什么额度耗尽要冻 key 而不是 provider。 免费额度是按模型的，同一个账号上往往既有已经枯竭的模型、也有还很富裕的模型。如果按 provider 冻，枯竭模型会把同 key 上的健康模型一起拖下水。所以枯竭停在 key 级，并且让枯竭模型排到 chain 后面，不占用候选名额。

为什么 JSON 校验要这么硬。 这一层现在扛着结构化抽取（长 prompt + 严格 schema），「静默抽空」是比报错更糟的失败模式。见下。

一个值得单独讲的坑：Schema 回显

上游的思考模型在小 max_tokens 下会把预算烧在 reasoning_content 里，然后把请求里的 JSON Schema 本体当成结果回显进 content，finish_reason=length。

而当时的校验只判「能不能 json.loads」——Schema 本身就是合法 JSON，于是判过，schema 被当成结果返回给上层，事实抽取静默抽空（facts=None），一条报错都没有。

修法是四件事一起做：

  1. 对照 schema 做一致性校验：required 齐全、顶层类型、enum、additionalProperties、嵌套 items 递归；
  2. 拒绝 schema 回显（键集 ⊆ Schema 关键字集）和 properties 片段回显（顶层每个值都像 Schema 节点）；
  3. 降级路径必须跑同一套校验——「降级」只改变怎么向上游要 JSON，不改变期望什么形状（这条最初被漏掉，导致降级候选的片段回显带着空事实直接过关）；
  4. 所有候选都不合格时回 502 relay_unusable_content，而不是最后一条上游的 200 体。

参数是按实测定的，不是抄默认值

这一层默认按「长 prompt 结构化抽取」调优（约 7KB 系统提示词、严格 schema、思考模型）：

参数 取值 依据
单次尝试超时 60s 思考模型一次真抽取要 16–50s，25s/45s 实测都会打满
思考模型最短超时 45s 会先思考再回答的模型
单请求总预算 110s 必须小于调用方自己的超时（我这边是 120s）
候选数上限 3 够扛两把坏 key，又不会撑爆预算
schema 请求 max_tokens 下限 1024 再低就会触发上面的 Schema 回显
provider 冷却 单次/硬封顶 120s / 300s 一次抖动不该停掉整个 provider

工程化

开源前补齐的东西，也是我觉得这套东西最该有的部分：

  • 106 项单测，零外部依赖，在 CI 的 Python 3.9 / 3.11 / 3.13 三档矩阵上跑；
  • mock_provider.py：假上游，行为由请求里的模型名决定，另有 6 种可注入场景（限流 / 挂起 / 空内容 / schema 回显 / 慢响应 / 常规），同时认多厂商路径形状——不用一把真 key、不烧一点额度就能把路由逻辑跑一遍；
  • 面板自检 40+ 组，包括用 CDP 真点按钮（「点了没反应」「输入到一半被重建冲掉」这类 bug 只有真点才发现）；
  • CI 里两道守卫：凭据文件守卫 + 个人痕迹/明文密钥扫描；
  • 文档截图全部由脚本用合成数据生成（两个假上游 + 一次性中继 + 临时面板），仓库里没有一张来自真实部署的截图。

两条踩坑记录

一、脱敏脚本的盲区。 扫描规则覆盖了绝对路径、私网 IP、密钥前缀，但漏掉了 ~/.hermes/... 这种「个人约定路径」——示例配置里就藏着一条。结论：自动扫描之后再跑一遍人工 grep，逐条判断「这是示例还是痕迹」。

二、截图「看起来是假的」。 我原来用「真渲染 ≥700KB」判截图真伪，那是带壁纸的界面留下的经验值；换成合成数据 + 纯色深色 UI 之后，真渲染只有 70–220KB，按老阈值会把好图全判成假的。现在判据是 DOM 断言：渲染出的 DOM 里必须出现该页的真实数据关键词，且不含「加载中」。
